Você é dev frontend no monorepo "Meu Barbeiro" (`web/` React 19 + Vite + Tailwind v4; `api/` Express + Prisma).

## Problemas (validados em homologação)

**P1 — Escolha de horário às cegas.** No passo "03 Quando?" (`web/src/features/client/ClientDashboard.tsx`) existe só um `<input type="datetime-local">`. O cliente adivinha um horário e só descobre que errou depois de submeter (erro 400/409). A API já expõe os horários livres:

`GET /appointments/availability?barberId=<uuid>&serviceId=<uuid>&date=YYYY-MM-DD`
```json
{ "date":"2026-08-05", "timezone":"America/Sao_Paulo", "open":true, "reason":null,
  "slots":[{ "scheduledAt":"2026-08-05T12:00:00.000Z", "label":"09:00" }] }
```

**P2 — Bug de fuso horário.** Hoje o formulário faz `new Date(event.target.value).toISOString()`, ou seja, interpreta o horário no fuso do NAVEGADOR. A API valida o expediente no fuso da BARBEARIA (`barbershop.timezone`). Um cliente em outro fuso escolhe "15:00" e reserva outro horário na barbearia, sem perceber. Usar os slots vindos da API (que já vêm como instante UTC correto) elimina essa conversão manual.

## Tarefa
1. Trocar o `datetime-local` por: um seletor de **data** (`<input type="date">`) + uma lista de **horários disponíveis** vinda da API. O `scheduledAt` enviado no POST passa a ser exatamente o `scheduledAt` do slot escolhido — sem nenhuma conversão de fuso no frontend.
2. Buscar a disponibilidade quando serviço + barbeiro + data estiverem preenchidos. Enquanto carrega, mostrar estado de carregando; se `open` for false ou `slots` vier vazio, mostrar o `reason` da API.
3. O botão de submeter fica desabilitado até haver um slot escolhido.
4. Mostrar o fuso da barbearia junto dos horários quando `timezone` for diferente do fuso do navegador (ex.: "horários no fuso da barbearia · America/Sao_Paulo"), para o cliente não se confundir.
