Você é dev backend no monorepo "Meu Barbeiro" (pnpm workspace: `api/` Express 5 + Prisma + zod; `web/` React 19 + Vite).

## Problema (validado em homologação)
No agendamento, o cliente só tem um `<input type="datetime-local">` cru. Ele precisa adivinhar um horário livre e só descobre que errou depois de submeter, recebendo 400 ("Escolha um horário entre 09:00 e 20:00" / "A barbearia não atende neste dia") ou 409 ("Este horário acabou de ser reservado"). É o maior atrito do produto.

## Tarefa (apenas backend)
Criar um endpoint que devolva os horários realmente disponíveis de um barbeiro num dia, para o frontend renderizar como lista de slots.

`GET /appointments/availability?barberId=<uuid>&serviceId=<uuid>&date=YYYY-MM-DD`

Regras:
- Reaproveite a autenticação e o contexto de barbearia já existentes no router (`requireUser`, `resolveBarbershop` — já aplicados via `router.use`).
- `date` é interpretada no fuso da barbearia (`barbershop.timezone`), não no fuso do servidor.
- Gere slots de 15 em 15 minutos dentro do expediente do dia (`businessHours` daquele weekday). Se o dia estiver desabilitado, devolva lista vazia com o motivo.
- Descarte slot que: já passou (com a mesma regra de "futuro" usada hoje), não cabe inteiro dentro do expediente considerando `service.duration`, ou colide com agendamento existente do mesmo barbeiro. Use `schedulesOverlap` e a MESMA condição de agendamentos "que ocupam horário" já usada no POST `/` (status PENDING/CONFIRMED e pagamento não expirado).
- Valide os query params com zod, no mesmo estilo do arquivo. `serviceId`/`barberId` inválidos → 400 com mensagem em português, igual ao POST.

Resposta:
```json
{
  "date": "2026-08-05",
  "timezone": "America/Sao_Paulo",
  "open": true,
  "reason": null,
  "slots": [{ "scheduledAt": "2026-08-05T12:00:00.000Z", "label": "09:00" }]
}
```
`reason` só é preenchido quando `open` é false ou quando não sobrou slot (ex.: "A barbearia não atende neste dia", "Não há horários livres nesta data"). `label` é o horário no fuso da barbearia.
