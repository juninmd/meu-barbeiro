Você é dev fullstack no monorepo "Meu Barbeiro" (`api/` Express 5 + Prisma + zod; `web/` React 19 + Vite).

## Por que esta tarefa existe
Os lembretes hoje avisam **só o cliente**. O barbeiro descobre que entrou horário, que alguém cancelou ou que a agenda mudou quando abre o app por conta própria — ou seja, tarde. Quem organiza o dia em cima da agenda precisa saber quando ela muda.

## 1. Notificações para a barbearia

Reaproveite a infraestrutura de `AppointmentReminder` e do serviço de envio já criados — **não crie um segundo mecanismo**. Generalize o registro para suportar destinatário barbeiro (o mesmo padrão de unicidade que impede envio repetido precisa continuar valendo).

Eventos que avisam o barbeiro responsável:
- **novo agendamento** para ele (inclusive vindo da fila de espera);
- **cancelamento** de um horário dele;
- **remarcação** que saiu ou entrou na agenda dele;
- **falta registrada** por outra pessoa da barbearia na agenda dele;
- **resumo do dia**, uma vez por dia, num horário configurável: quantos clientes, primeiro e último horário, buracos na agenda.

Dono/admin recebem, além disso, o que afeta a operação: cancelamento em qualquer agenda e resumo consolidado.

## 2. Regras

- Só envia para quem tem canal vinculado (`telegramId`), e o registro guarda sucesso e erro, sem derrubar a leva — igual aos lembretes.
- **Nada de spam**: agrupe eventos próximos. Cinco cancelamentos em dois minutos viram uma mensagem, não cinco. Defina uma janela de agrupamento curta e justifique o valor escolhido no resumo.
- Cada pessoa escolhe o que quer receber: em `Membership` ou numa tabela de preferência, guarde quais tipos de aviso o barbeiro aceita. Silenciar precisa ser possível, senão a pessoa desliga tudo.
- Ação do próprio barbeiro **não gera aviso para ele mesmo**: quem acabou de lançar o horário não precisa ser avisado do horário que lançou.
- O resumo do dia sai no fuso da barbearia.
- Continua tudo sob a mesma flag de ambiente e no mesmo laço interno já existente. Sem agendador novo, sem dependência nova.

## 3. Frontend

- Nos ajustes do usuário da barbearia, escolher quais avisos receber e o horário do resumo diário.
- Deixe visível para o barbeiro quando seu canal **não** está vinculado — aviso que não chega é pior que aviso que não existe, porque cria falsa segurança.

## Restrições
- Mudança cirúrgica: não refatore o que não é necessário, não reformate arquivos, não adicione dependência nova.
- Não regrida nada existente, em especial os lembretes do cliente.
- Siga o estilo do código existente (sem ponto e vírgula, aspas simples, textos em português).
- Nunca envie de verdade em teste: use a injeção da função de envio já adotada.

## Testes
- Cada evento gera aviso para o barbeiro certo, e só para ele.
- Ação do próprio barbeiro não gera aviso para ele.
- Eventos próximos são agrupados numa mensagem só.
- Quem silenciou um tipo não recebe aquele tipo, e continua recebendo os outros.
- Barbeiro sem canal não gera erro que interrompa a leva.
- Resumo do dia sai uma vez só e no fuso da barbearia.
- Testes independentes do fuso da máquina e sem rede.

## Critério de aceite (rode e conserte até passar)

```
cd api && pnpm exec prisma migrate dev --name <nome-da-migracao>
cd api && pnpm exec tsc --noEmit
cd api && pnpm test
cd web && pnpm exec tsc --noEmit
cd web && pnpm lint
cd web && pnpm test
cd web && pnpm build
```
Ao terminar, escreva um resumo do que mudou e o resultado real dos comandos.
